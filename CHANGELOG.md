# Changelog

Notable user-facing changes are recorded here. The project is pre-release; entries are grouped under `Unreleased` until a version is published.

## Unreleased

### Added

- `devdock up` now starts a project one dependency layer at a time, waiting between layers, so the ordering is DevDock's rather than Compose's and a blocked service can be named. A project with no dependencies, or one that is already running, still goes out in a single call, so a repeat `up` reconciles as before. `--no-stage` restores the single-call behaviour and `--max-parallel` bounds how much Compose does at once. When the Compose file's dependencies cannot be read, DevDock does not guess: it starts everything in one call and leaves Compose's ordering in charge.
- `devdock up` now waits for services to become ready and reports what proved each one ready. The dependency graph is built and validated **before** anything is started, so a cycle, a dependency that does not exist, or a condition that can never be met is a refusal rather than a wait that never ends. `--no-wait` starts without waiting, `--require-ready` refuses to accept a service with nothing to verify it, and `--ready-timeout`/`--deadline` bound a single service and the whole startup. A service's own timeout is counted from when its dependencies are satisfied, not from when the command started.
- `devdock wait`, which waits for an already-started project without starting anything. For use after an interrupt, from a second terminal, or in a script that started the project some other way.
- A gated fault-injection suite for readiness: a service whose health check never passes, a probe that never answers, a service that becomes healthy and then dies, a dependency condition that can never be met, a diamond graph, a cycle only the merged graph can see, and an interrupt mid-wait. These check against a real daemon the premises the unit tests assume about how Docker reports health.
- The demo project now shows every readiness class in one run: a one-shot task that exits cleanly, a service verified by both a health check and an HTTP probe, and one with nothing to verify it.
- Interrupting `devdock up`, `devdock wait`, or `devdock down` with Ctrl+C (or Ctrl+Break on Windows) now stops the operation deliberately and exits `130` on every platform, reporting `UP_INTERRUPTED` or `DOWN_INTERRUPTED` with what may exist and what to run next. Nothing is torn down. A second interrupt exits at once with the same status.
- The readiness wait engine behind milestone 3: it polls every service, reports which dependency is blocking which, and ends with a verdict rather than a hang. A service's own timeout starts when it is running and unblocked, not when the wait began, so a service deep in the graph is not charged for its ancestors' slowness. A service that had become ready and then exits or goes unhealthy fails the wait immediately instead of letting every dependent time out in turn; one that merely drops back to starting is counted as flapping and waited through. A condition that can never be met -- waiting for health on a service that reports none, or completion of one that exited non-zero -- is named instead of waited out. Its clock, observations, and cancellation are all injected, which is what lets slow starts, flapping and deadlines be tested without waiting for any of them.
- `devdock status` now evaluates every readiness source a service has and shows each one's result. A service is `ready` only when its Compose health, if it reports any, and every `tcp`/`http` probe declared for it in `devdock.yaml` all agree; a service with no source at all is still reported as running rather than ready. Only running services are probed, and a probe failing on a port the service does not publish is called out, since probing the container's port instead of the published one is the usual mistake. A new `exited cleanly` class separates an exit code of `0` from any other.
- TCP and HTTP readiness probes. Each makes one bounded attempt and reports a phrase from a closed vocabulary; nothing the endpoint sends is ever repeated. Before connecting, the declared host is re-checked against the loopback rule and resolved, every resolved address must be loopback, and the checked address is the one contacted. HTTP probes send no credentials or cookies, ignore proxies configured in the environment, do not follow redirects, and never read the response body. A port that is open but hangs up is reported as exactly that, since it is what a service does while it is still starting.
- Reading a project's real dependencies from Compose. The adapter runs `docker compose config --format json --no-interpolate` and keeps four facts: service names, `depends_on` edges with their condition and Compose's `required` flag, and which services declare or disable a health check. `--no-interpolate` is a safety control: without it Compose expands `${VAR}` from the shell and the project's `.env` and resolves every `env_file` into the output, so the document would carry the project's secrets. Nothing else from it is retained, and a failed listing reports an exit status rather than the runtime's text.
- The merged dependency graph behind the readiness work: Compose-declared and profile-declared dependencies are combined (both are honored, and the stricter condition wins where they are comparable) into sorted startup layers. Undeclared services, contradictory conditions, waits for health on a service that disables its health check, and dependency cycles are all reported together in one pass, each cyclic group showing a concrete path, before anything is started.
- An optional `services` block in `devdock.yaml` for declaring per-service dependencies (`depends_on`, with Compose's conditions plus DevDock's `service_ready`) and readiness probes (`tcp` and `http`). `depends_on` gives `up` and `wait` their startup order; `readiness` is probed by `up`, `wait`, and `status`. Probes may only target loopback, carry a bounded timeout, and there is no probe type that runs a command.
- A gated Docker integration suite (`pytest -m docker`) that exercises the real runtime with disposable resources and verifies the Compose labels, `compose ps` JSON fields, and failure-taxonomy markers that unit tests can only fake. Deselected by default; skips when no daemon is reachable.
- `examples/demo`, a disposable sample project, and `scripts/demo.py`, a scripted walkthrough of the full lifecycle including the ownership refusal and volume preservation.
- `python -m devdock` as an alternative to the installed script.

- Failure taxonomy for `up` and `down`: permission, daemon, configuration, registry auth, image, pull, port, network, host-resource, in-use, and service failures each get a stable code and a specific suggested action. Recognized failures withhold the runtime's output, since the code already explains the problem.
- Shape-based redaction for credentials DevDock has never seen, including private keys, JWTs, cloud and provider tokens, `Bearer` headers, and secret-named `key=value` pairs.
- `CODE_OF_CONDUCT.md`.
- `devdock --version`. Terminal output neutralizes control characters from container names and runtime data. The package ships a `py.typed` marker.
- `devdock down` previews, confirms, then stops and removes a project's DevDock-managed containers and networks, re-checks what remains, and never removes volumes. Supports `--dry-run` and `--yes`.
- `devdock status` reports each declared service's container, state, Compose health, readiness class, and published ports, lists resources DevDock does not own, and distinguishes running from ready.
- `devdock up` starts a project's Compose services detached after passing diagnostic, Compose-file, runtime, and ownership gates. Captured Docker output is hidden by default, redacted on every path, and shown in full only with `--show-output`.
- Ownership scope: a deterministic Compose project name per project root, printed by `devdock inspect`, and label-based rules that future lifecycle commands use to refuse resources DevDock did not create.
- Structured discovery evidence, nested-root reporting, and safe project manifest/Python metadata inspection.
- Coded diagnostics for Python interpreter evidence, Docker/Compose availability and parsing, required paths, environment state, and TCP ports.
- Explicit skipped-check findings when Docker prerequisites or safe Compose inputs are unavailable; Docker command output is not exposed.
- `devdock init`, `devdock inspect`, and `devdock check` for local project profiles.
- Version 1 YAML profile validation and read-only checks for declared Python, Docker Compose, Compose file, and environment-name requirements.
- CLI behavior, architecture, installation, contribution, and security documentation.
- Cross-platform quality workflow for Python 3.12–3.14 on Linux, macOS, and Windows.

### Fixed

- `devdock up` reported a completed one-shot service by its internal name while `devdock status` called the same state `exited cleanly`. Both now use the display label.
- Docker commands ran in DevDock's own process group, so a terminal's Ctrl+C went straight to `docker` as well — the terminal, not DevDock, was interrupting an operation part-way through, and DevDock only found out afterwards. Each command now runs in a group of its own. On POSIX the whole group is signalled when a command is cancelled or times out, so a helper process is not left behind, and no exit path can leave a running child.
- Captured command output was unbounded. It is now written to a temporary file instead of a pipe, so a command cannot stall on a full buffer and partial output survives a timeout, and at most 1 MB is read back. Line endings are normalized so Windows and POSIX output are the same string.
- A readiness probe with a non-ASCII `path` crashed `devdock status` with a traceback instead of reporting a result: the HTTP client rejects such a request with a `ValueError`, which is neither a transport error nor one the probe module raises. Those paths are now refused when the profile loads, a `#` fragment is refused with them, and the probe treats any remaining `ValueError` as an unreadable response rather than letting it escape a read-only command.
- The Compose health value was the one piece of runtime text interpolated into a status report. It is now classified against a fixed set like every other source.
- Parsing JSON from Docker raised an unhandled `RecursionError` on deeply nested input, which is not a decode error and so escaped as a traceback. Compose echoes `x-` extension fields verbatim and they accept any structure, so the nesting can come from a project file. Both the configuration and service-status parsers now refuse it.
- `devdock init` templated the project name into YAML unquoted, so a directory named `true`, `1.0`, or `a: b` produced a profile that failed validation. The profile is now serialized.
- `down` reported `DOWN_PARTIAL` after correctly leaving an undeclared running container in place, because that container kept the project network alive. The plan now says the network will stay, and the verification expects it.
- `UP_TIMED_OUT` referred to a `docker ps` command that was not always printed. It is now included in the evidence.
- The `DOCKER_DAEMON_AVAILABLE` evidence still mentioned `docker info` after the probe switched to `docker version`.
- `up` and `down` printed the runtime's raw progress output on success, contradicting the documented contract and showing duplicated Compose lines. Output on success now waits behind `--show-output`, as documented.
- A port probe that failed during `up` preflight printed as `[FAIL]` inside an `[OK]` result. It now prints as `[ADVISORY]` with an explanation that it did not block the start.
- The failure taxonomy did not recognize `context deadline exceeded`, Go's standard timeout wording and what Docker reports for a registry it cannot reach, so an unreachable registry fell through to `UP_FAILED`. Registry connection markers were added and verified against a real daemon.
- DevDock reported `DOCKER_DAEMON_AVAILABLE` when the daemon socket could not be opened. The probe relied on the exit status of `docker info`, which is zero even when the server is unreachable, so `check` passed, `up` proceeded to refuse with an ownership conflict, and the Docker test suite ran instead of skipping. Reachability now requires a server version from `docker version`, and a socket the user may not open is reported as `DOCKER_DAEMON_PERMISSION_DENIED` with the group and re-login remedy. The suite and the demo use the same detection.
- `devdock up` refused to run a second time when the profile declared a port its own services publish. Port probes are now advisory during the start preflight; Compose's own bind remains authoritative and reports `UP_PORT_CONFLICT`.
- Redaction could stall on long runtime output. The URL-credential pattern had an unbounded scheme run and backtracked quadratically; 256 KB of plain text took over a minute. All patterns are now bounded and a regression test asserts linear behavior.
- Hardening from the Milestone 2 review: Compose runs with `COMPOSE_REMOVE_ORPHANS` pinned off so a project `.env` cannot widen `down`; `down` re-verifies the plan immediately before acting and reports `DOWN_PARTIAL` when it cannot confirm the result; inventory fields are JSON-encoded so labels cannot forge records; profile paths reject control characters; redaction skips well-known non-secret variables and cannot mangle its own placeholders.
